# ตู้บริการข้อมูลอัจฉริยะ (Smart Kiosk)

ตู้บริการข้อมูลของ **สาขาวิชาวิทยาการคอมพิวเตอร์ คณะวิทยาศาสตร์ มหาวิทยาลัยแม่โจ้**
นักศึกษายืนหน้าตู้แล้วดูตารางเรียนของตนเองได้ทันที โดยไม่ต้องเข้าสู่ระบบหรือพิมพ์ข้อความ
พร้อมผู้ช่วยตอบคำถามเกี่ยวกับสาขาและอาคาร สั่งงานได้ทั้งการแตะและเสียง

ติดตั้งใช้งานบน Raspberry Pi 5 · จอสัมผัสแนวตั้ง 1080×1920 · Chromium kiosk mode

---

## หลักการออกแบบที่กำหนดทุกอย่างในโปรเจกต์นี้

**1. แยกประเภทคำถามก่อนตอบ**
คำถามที่มีคำตอบแน่นอน (ตารางเรียน ห้องเรียน กำหนดสอบ) ค้นจาก SQLite โดยตรง **ไม่ผ่าน AI**
จึงไม่มีโอกาสตอบผิด และยังทำงานได้เมื่ออินเทอร์เน็ตขัดข้อง
คำถามทั่วไปจึงส่งให้ผู้ช่วย AI ซึ่งถูกบังคับให้อ้างอิงเอกสารเสมอ

**2. ผู้ช่วย AI เขียนข้อความอ้างอิงเองไม่ได้**
โมเดลทำได้แค่เลือกหมายเลขชิ้นเอกสารที่ใช้ตอบ แล้วเซิร์ฟเวอร์ไปดึงชื่อเอกสารจากฐานข้อมูลมาแสดงเอง
ต่อให้โมเดลแต่งชื่อเอกสารขึ้นมา ก็ไม่มีทางหลุดออกหน้าจอ
ถ้าค้นเอกสารไม่เจอหรือเรียก API ไม่สำเร็จ ระบบตอบ "ไม่พบข้อมูลนี้ในระบบ" — ไม่เดาคำตอบ

**3. กฎความเป็นส่วนตัวบังคับที่ระดับฐานข้อมูล ไม่ใช่แค่ในโค้ด**
`face_embeddings.consent_id` เป็น `NOT NULL` + FK ไปยัง `consents`
เขียนเวกเตอร์ใบหน้าโดยไม่มีความยินยอมจึงทำไม่ได้เลย และการถอนความยินยอมลบเวกเตอร์ตามไปทันที
ไม่มีคอลัมน์ใดเก็บ "ภาพ" ใบหน้า และ `usage_events` ไม่มี FK ไป `students` โดยเจตนา

**4. หน้าเว็บบอกไม่ได้ว่า "ฉันคือใคร"**
บอกได้แค่ว่ากดยืนยันผู้ที่ระบบเสนอมา (candidateToken ใช้ได้ครั้งเดียว อายุ 45 วินาที)
รหัสนักศึกษาเต็มไม่เคยออกจากเซิร์ฟเวอร์ — ส่งเฉพาะรูปแบบปิดบัง `••••1001`

## เริ่มพัฒนา

ต้องมี **Python 3.11+** และ **Node.js 20+**

### 1. เซิร์ฟเวอร์

```bash
cd server
python -m venv .venv
.venv/Scripts/python.exe -m pip install -r requirements.txt   # Windows
# source .venv/bin/activate && pip install -r requirements.txt  # Linux/Pi

cp .env.example .env            # แก้ค่าตามต้องการ (ไม่ใส่ก็ใช้ค่าตั้งต้นได้)
.venv/Scripts/python.exe -m app.seed --reset       # นำเข้าข้อมูลจริง + สร้างตารางเรียนสาธิต
.venv/Scripts/python.exe -m uvicorn app.main:app --reload --port 8000
```

เปิดเอกสาร API อัตโนมัติได้ที่ http://127.0.0.1:8000/docs

### 2. หน้าจอ

```bash
cd web
npm install
npm run dev
```

เปิด http://localhost:5173 — Vite ส่งต่อ `/api` และ `/ws` ไปยังพอร์ต 8000 ให้เอง

### 3. ทดสอบ

```bash
cd server
.venv/Scripts/python.exe scripts/smoke.py             # API 37 ข้อ
.venv/Scripts/python.exe scripts/test_retrieval.py    # ค้นเอกสารภาษาไทย 7 ข้อ
.venv/Scripts/python.exe scripts/test_intent.py       # ตีความคำถามจากเสียง 19 ข้อ
.venv/Scripts/python.exe scripts/test_face.py --check # ตรวจข้อมูลใบหน้าในระบบ

cd ../web && npm run e2e                              # ขับหน้าจอจริง ~41 ข้อ
```

ทั้งหมดนี้ไม่ต้องใช้กุญแจ API และไม่ต้องมีคนอยู่หน้ากล้อง

> จำนวนข้อของ `npm run e2e` เปลี่ยนตามสิ่งที่กล้องเห็นจริงในขณะนั้น
> ถ้ามีคนที่ลงทะเบียนใบหน้าไว้อยู่หน้าจอ ชุดทดสอบจะเดินเส้นทาง "จำได้ → ยืนยันตัวตน"
> ถ้าไม่มี จะเดินเส้นทาง "จำไม่ได้ → กรอกรหัสนักศึกษา" ทั้งสองทางถือว่าผ่าน

**ทดสอบกล้องด้วยตัวเอง** (ต้องนั่งอยู่หน้ากล้อง)

```bash
cd server
.venv/Scripts/python.exe scripts/test_face.py --enroll 6604101001   # ลงทะเบียนใบหน้าให้รหัสนี้
.venv/Scripts/python.exe scripts/test_face.py --recognize           # ดูคะแนนการจำแบบเรียลไทม์
```

`scripts/e2e.mjs` ใช้ Chrome/Edge/Chromium ที่ติดตั้งอยู่แล้วในเครื่อง ไม่ดาวน์โหลดเบราว์เซอร์เพิ่ม
เพิ่ม `--shots ./shots` เพื่อเก็บภาพหน้าจอทุกขั้น หรือ `--headed` เพื่อดูเบราว์เซอร์ทำงาน

## สองโหมดการแสดงผล

หน้าจอของตู้จริงเป็นแนวตั้ง 1080×1920 แต่ตอนพัฒนาบน Windows จอเป็นแนวนอน
ถ้าย่อทั้งเวทีให้พอดีความสูงจะเหลือเป็นแถบแคบ ๆ กลางจอดำ ใช้งานลำบาก

`Stage` จึงเลือกโหมดจากสัดส่วนหน้าจอเอง

| โหมด | เมื่อไหร่ | หน้าตา |
| --- | --- | --- |
| `kiosk` | จอสูงกว่ากว้าง (ตู้จริง) | เวที 1080×1920 ย่อให้พอดีทั้งจอ |
| `desktop` | จอกว้างกว่าสูง (Windows) | แผงคู่สนทนาซ้าย + หน้าจอตู้ขวา |

**ทั้งสองโหมดใช้หน้าจอชุดเดียวกัน** ขนาดตัวอักษรและเป้าแตะจึงยังตรงตามข้อกำหนดเสมอ
(เนื้อหา ≥ 24px · หัวข้อ ≥ 40px · เป้าแตะ ≥ 72×72px)
โหมด `desktop` แค่เอาพื้นที่ว่างด้านข้างมาใช้ประโยชน์ ไม่ได้แก้เนื้อหาข้างใน
จึงไม่มีทางที่หน้าจอบนตู้จริงกับบนเครื่องพัฒนาจะเพี้ยนไปคนละทาง

### แผงคู่สนทนา (PresencePanel)

แผงด้านซ้ายในโหมด `desktop` ทำหน้าที่เป็น "คู่สนทนา" ของนักศึกษา

- ภาพสดจากกล้อง **กลับด้านเหมือนส่องกระจก** เพราะผู้ใช้ขยับตัวตามภาพที่เห็น
- วงแหวนรอบภาพเปลี่ยนสีตามสถานะ: พร้อมฟัง / กำลังฟัง / กำลังคิด
- บทสนทนาเป็นบับเบิลสองฝั่ง — สิ่งที่ตู้ได้ยิน กับสิ่งที่ตู้ตอบ

บนตู้จริงไม่มีพื้นที่ด้านข้าง หน้าผู้ช่วยจึงแสดงภาพกล้องขนาดย่อข้างปุ่มไมโครโฟนแทน
เฉพาะตอนกำลังพูดคุย เพื่อให้รู้สึกเหมือนคุยกับใครสักคน ไม่ใช่พูดใส่ปุ่มเปล่า ๆ

## กล้อง ใบหน้า และเสียง

### กล้องเป็นของเซิร์ฟเวอร์ ไม่ใช่ของเบราว์เซอร์

การรู้จำใบหน้าทำงานฝั่ง Python อยู่แล้ว การส่งเฟรมวิดีโอจากเบราว์เซอร์มาประมวลผลจึงเสียเปล่า
และ Chromium โหมด kiosk บน Raspberry Pi ขออนุญาตใช้กล้องยุ่งยาก
หน้าเว็บจึงดูภาพสดผ่านสตรีม MJPEG ที่ `/api/face/stream` ซึ่งใส่ใน `<img>` ได้เลย

| ขั้นตอน | ทำอะไร |
| --- | --- |
| ตรวจจับ | SCRFD หาตำแหน่งใบหน้า (~4 ms บนโน้ตบุ๊ก · คาดว่า ~50–150 ms บน Pi 5) |
| แปลงเป็นเวกเตอร์ | ArcFace แปลงใบหน้าเป็นตัวเลข 512 มิติที่ normalise แล้ว |
| เทียบ | cosine similarity กับเวกเตอร์ที่ลงทะเบียนไว้ |

**กติกาการตัดสินว่า "ใช่คนนี้" ต้องผ่านสองด่าน**

1. คะแนนสูงกว่าเกณฑ์ (`KIOSK_FACE_THRESHOLD`, ค่าตั้งต้น 0.45)
2. ห่างจากอันดับสองอย่างน้อย `KIOSK_FACE_MARGIN` (ค่าตั้งต้น 0.05)

ด่านที่สองมีไว้แก้ความเสี่ยง **"ระบบรู้จำใบหน้าผิดคน"** ที่ระบุไว้ในเอกสารโดยตรง
เพราะการทักผิดคนแล้วแสดงตารางเรียนของคนอื่น คือการเปิดเผยข้อมูลส่วนบุคคล
ถ้าคะแนนอันดับ 1 กับ 2 ใกล้กันเกินไป ระบบจะตอบว่า "จำไม่ได้" แทนการเดา

### ลำดับการลงทะเบียนใบหน้า — ถ่ายก่อน กรอกรายละเอียดทีหลัง

```
จำใบหน้าไม่ได้ → "ลงทะเบียนใบหน้า" → ขอความยินยอม → ถ่าย 8 ใบ → กรอกรหัสนักศึกษา → เสร็จ
```

กล้องจ่ออยู่ที่หน้าผู้ใช้อยู่แล้ว การให้ถ่ายเลยจึงเป็นธรรมชาติกว่าการบังคับกรอกรหัสก่อน
และเวลาที่เสียไปกับการกรอกรหัส 10 หลักก็ไม่ต้องให้ยืนค้างอยู่หน้ากล้อง

| ขั้น | เกิดอะไรขึ้น |
| --- | --- |
| 1 · ยินยอม | แตะช่องยินยอมเอง (ห้ามติ๊กไว้ล่วงหน้า) เวลาที่กดถูกจำไว้ที่เซิร์ฟเวอร์ |
| 2 · ถ่าย | เก็บตัวอย่าง 8 ใบ เวกเตอร์ถูก**พักไว้ในหน่วยความจำ ยังไม่เขียนลงดิสก์** |
| 3 · กรอกรหัส | บอกว่าใบหน้านี้เป็นของรหัสใด แล้วบันทึกความยินยอม + เวกเตอร์พร้อมกันในรายการเดียว |

**ความยินยอมยังต้องมาก่อนการถ่ายเสมอ** เพราะ พ.ร.บ.คุ้มครองข้อมูลส่วนบุคคลฯ มาตรา 26
กำหนดไว้สำหรับข้อมูลชีวภาพ สิ่งที่ย้ายไปอยู่ท้ายสุดคือ "รหัสนักศึกษา" ไม่ใช่ความยินยอม

ผลพลอยได้ด้านความปลอดภัย: **ไม่มีเวกเตอร์ใบหน้าแตะดิสก์เลย จนกว่าจะมีความยินยอมผูกกับตัวบุคคล**
ถ้าผู้ใช้เดินจากไปกลางคัน ข้อมูลที่พักไว้หมดอายุใน 3 นาทีแล้วหายไปเอง

ถ้ายืนยันตัวตนอยู่แล้ว (กดลงทะเบียนจากหน้าหลัก) จะข้ามขั้นกรอกรหัส เพราะเซิร์ฟเวอร์รู้จากเซสชันแล้ว

ครั้งถัดไปนักศึกษายืนหน้าตู้แล้วระบบจำได้ทันที ไม่ต้องกรอกรหัสอีก

### เก็บอะไรบ้างตอนลงทะเบียนใบหน้า

เก็บเวกเตอร์ 512 มิติที่เฉลี่ยจากตัวอย่าง 8 ใบเท่านั้น **ไม่มีการบันทึกภาพหรือวิดีโอ**
ก่อนบันทึกระบบตรวจสองอย่าง

- ตัวอย่างทั้ง 8 ใบต้องสอดคล้องกันไม่น้อยกว่า 0.60 ไม่งั้นให้ถ่ายใหม่
- เวกเตอร์ที่ได้ต้องไม่ตรงกับผู้ที่ลงทะเบียนไว้แล้ว มิฉะนั้นปฏิเสธ

> ⚠️ **ช่องโหว่ที่ยังเหลืออยู่ และต้องแก้ด้วยกระบวนการ ไม่ใช่โค้ด**
> การลงทะเบียนใช้การกรอกรหัสนักศึกษาเป็นตัวระบุตัวตน ซึ่งไม่ได้ยืนยันว่าเป็นเจ้าของรหัสจริง
> ระบบจึงกันไว้ว่า **รหัสที่มีข้อมูลใบหน้าอยู่แล้วลงทะเบียนซ้ำไม่ได้** (HTTP 409)
> ผู้ที่ต้องการลงทะเบียนใหม่ต้องไปลบข้อมูลเดิมที่สำนักงานสาขาก่อน
> การแก้ให้สมบูรณ์คือให้เจ้าหน้าที่ยืนยันตัวตนตอนลงทะเบียนครั้งแรก

### เสียงพูดภาษาไทย

ใช้ **faster-whisper** ทำงานบนเครื่องของตู้เอง ไม่ต้องต่ออินเทอร์เน็ต
ไม่ใช้ Web Speech API ของเบราว์เซอร์ เพราะ Chromium บน Raspberry Pi ไม่มีบริการรู้จำเสียงให้ใช้
ถ้าพึ่งมันแล้วย้ายไปลงตู้จริง ฟีเจอร์เสียงจะใช้ไม่ได้ทันที

| | |
| --- | --- |
| อัดเสียง | เบราว์เซอร์ใช้ `MediaRecorder` (webm/opus) ส่งผ่าน `/ws/voice` |
| ถอดรหัส | PyAV ที่ติดมากับ faster-whisper — ไม่ต้องลง ffmpeg และไม่ต้องเขียน AudioWorklet |
| ถอดความ | รุ่น `base` int8 · ~0.5–1.5 วิ บนโน้ตบุ๊ก · คาดว่า ~2–5 วิ บน Pi 5 |
| ตีความคำถาม | คำสำคัญก่อน แล้วค่อยวัดความคล้ายตัวอักษร (`app/services/intent.py`) |

**ไม่มีการบันทึกไฟล์เสียงลงดิสก์** เสียงอยู่ในหน่วยความจำจนถอดความเสร็จแล้วถูกทิ้ง
และไม่มีการเก็บข้อความที่ถอดได้ลงฐานข้อมูล สถิติที่บันทึกมีแค่ประเภทคำถาม ช่องทาง และแหล่งคำตอบ
เหมือนตอนแตะปุ่มทุกประการ

การถอดเสียงทำในเครื่อง จึง**พูดถามตารางเรียนได้แม้ตู้ออฟไลน์** มีเพียงคำถามที่ต้องใช้ผู้ช่วย AI
เท่านั้นที่ถูกปิดตอนไม่มีอินเทอร์เน็ต

คำถามที่ระบบจับคู่กับปุ่มไม่ได้ จะถูกส่งให้ผู้ช่วย AI ค้นเอกสารของสาขาตอบ
โดยยังต้องอ้างอิงเอกสารเสมอตามกติกาเดิม ถ้าค้นไม่เจอจะได้ "ไม่พบข้อมูลนี้ในระบบ"

## หน้าจอบนคอมพิวเตอร์ Windows

ตู้จริงเป็นจอแนวตั้ง 1080×1920 แต่ตอนพัฒนาบน Windows จอเป็นแนวนอน
ถ้าย่อทั้งเวทีให้พอดีความสูงจะเหลือเป็นแถบแคบ ๆ กลางจอดำ ใช้งานลำบาก

`Stage` จึงมีสองโหมด และใช้หน้าจอชุดเดียวกันทั้งคู่
ขนาดตัวอักษรและเป้าแตะจึงยังตรงตามข้อกำหนดเสมอ ไม่ว่าดูบนเครื่องไหน

| โหมด | เมื่อไร | หน้าตา |
| --- | --- | --- |
| kiosk | จอสูงกว่ากว้าง (ตู้จริง) | ย่อเวทีให้พอดีจอ เหมือนเดิม |
| desktop | จอกว้างกว่าสูงตั้งแต่ 1.15 เท่า | แผงด้านข้างซ้าย + หน้าจอตู้ขวา |

แผงด้านข้างไม่ได้มีไว้เติมที่ว่างเฉย ๆ แต่ทำหน้าที่เป็น **คู่สนทนา** —
นักศึกษาเห็นหน้าตัวเองอยู่ตรงข้าม พร้อมสิ่งที่ตู้ได้ยินและสิ่งที่ตู้ตอบ
เหมือนคุยกันอยู่คนละฝั่งโต๊ะ ไม่ใช่พูดใส่จอเปล่า ๆ

บนตู้จริงที่ไม่มีพื้นที่ด้านข้าง หน้าผู้ช่วยจะแสดงภาพกล้องขนาดย่อข้างปุ่มไมโครโฟน
ระหว่างที่กำลังฟังหรือกำลังคิด เพื่อให้ได้ความรู้สึกเดียวกัน

หน้าผู้ช่วยตอบคำถามเป็นหน้าต่างแชทเต็มรูปแบบ (`components/ChatWindow.jsx`)
ใช้รูปแบบเดียวกับแอปแชททั่วไป เพราะนักศึกษาคุ้นอยู่แล้ว ไม่ต้องเรียนรู้ใหม่

```
┌──────────────────────────────────────┐
│ ●  ผู้ช่วยตอบคำถาม               ✕  │  รูปผู้ใช้จากกล้อง + ปุ่มปิด
├──────────────────────────────────────┤
│                    ┌───────────────┐ │  ฟองเขียว = นักศึกษา
│                    │ คำถาม         │ │
│  ┌──────────────┐  └───────────────┘ │  ฟองขาว = ตู้ (มีป้ายบอกที่มา)
│  │ 🗄 จากระบบ    │                    │
│  │ คำตอบ        │                    │
│  └──────────────┘                    │
├──────────────────────────────────────┤
│  ถามอะไรก็ได้…                       │
│  🎤   🗄                          ➤  │  พูด · คำถามยอดนิยม · ส่ง
└──────────────────────────────────────┘
```

### ถามได้สามทาง ผ่านกติกาเดียวกันหมด

| ช่องทาง | ส่งอะไรไป | หมายเหตุ |
| --- | --- | --- |
| แตะ | `questionId` ของปุ่มคำถามยอดนิยม | เปิดแผงได้จากปุ่มฐานข้อมูลข้างช่องพิมพ์ |
| พิมพ์ | `text` ที่ผู้ใช้พิมพ์ | ใช้ตัวตีความชุดเดียวกับเสียง |
| พูด | เสียงผ่าน `/ws/voice` | ถอดความแล้วเข้าตรรกะเดียวกัน |

คำถามที่พิมพ์เองผ่าน `app/services/intent.py` ก่อนเสมอ **คำถามเรื่องตารางเรียน
ห้องเรียน และกำหนดสอบจึงยังไปที่ฐานข้อมูลโดยตรง ไม่ถูกส่งให้ AI เดา**
เหลือเฉพาะคำถามปลายเปิดที่ไปถึงผู้ช่วย AI ซึ่งยังต้องอ้างอิงเอกสารเสมอ

ช่องพิมพ์มีประโยชน์มากตอนพัฒนาบน Windows เพราะทดสอบคำถามได้โดยไม่ต้องพูด
บนตู้จริงที่ไม่มีแป้นพิมพ์ ช่องทางหลักยังเป็นการพูดและการแตะปุ่มตามเดิม

### บทสนทนาไม่ถูกเก็บ

ฟองข้อความทั้งหมดอยู่บนหน้าจอเท่านั้น **ไม่ส่งขึ้นเซิร์ฟเวอร์และไม่บันทึกลงฐานข้อมูล**
เมื่อออกจากระบบหรือหมดเวลาใช้งาน ถูกล้างทิ้งพร้อมข้อมูลอื่น
ข้อความที่ผู้ใช้พิมพ์ก็ไม่ถูกบันทึกเช่นกัน สถิติที่เก็บยังมีแค่ประเภทคำถาม
ช่องทาง และแหล่งคำตอบ เหมือนการแตะปุ่มทุกประการ

## ปรับโครงฐานข้อมูลของตู้ที่ติดตั้งไปแล้ว

`schema.sql` ใช้ `CREATE TABLE IF NOT EXISTS` จึงสร้างตารางใหม่ได้อย่างเดียว
แก้ตารางที่มีอยู่แล้วไม่ได้ `app/migrations.py` รับหน้าที่นั้น และถูกเรียกทุกครั้งที่เริ่มเซิร์ฟเวอร์

ทุกขั้นตอนต้องเรียกซ้ำได้โดยไม่เกิดผลข้างเคียง เพราะตู้ที่ให้บริการแล้วมีเวกเตอร์ใบหน้า
และบันทึกความยินยอมอยู่ ซึ่งลบทิ้งไม่ได้ — ผู้ใช้จะต้องมาลงทะเบียนใหม่ทั้งหมด

## แผงตัวควบคุมทดสอบ

แตะแถบเล็ก ๆ ที่ **ขอบขวาของจอ (กึ่งกลางแนวตั้ง)** เพื่อเปิดแผงจำลองสถานะ

| กลุ่ม | ปุ่ม |
| --- | --- |
| เซ็นเซอร์ | ตรวจพบคน (ปลุกจอ) · เข้าสู่จอพักลึก |
| ใบหน้า | จำหน้าได้ · จำหน้าไม่ได้ · พบหลายใบหน้า · หาใบหน้าไม่เจอ · กล้องใช้งานไม่ได้ · สลับผู้ใช้ |
| เครือข่าย | ออนไลน์ · ออฟไลน์ |
| เสียง | กำลังฟังเสียง · ฟังไม่ชัด |
| ข้อมูล | ไม่มีข้อมูลตารางเรียน · รีเซ็ตทั้งหมด |

ปุ่มเหล่านี้ไม่ได้เปลี่ยนสถานะในหน้าเว็บโดยตรง แต่ยิงไปที่ `/api/sim/*`
แล้วเซิร์ฟเวอร์ผลักเหตุการณ์กลับมาทาง WebSocket **เส้นทางเดียวกับที่กล้องจริงจะใช้**
เมื่อกล้องมาถึงจึงเปลี่ยนแค่ผู้ผลิตเหตุการณ์ ไม่ต้องแก้หน้าจอ

> ⚠️ ตั้ง `KIOSK_SIM=0` เมื่อติดตั้งบนตู้จริง มิฉะนั้นใครก็ยิง `/api/sim/face/recognized`
> เพื่อสวมรอยเป็นนักศึกษาคนใดก็ได้

## API

| เส้นทาง | หน้าที่ |
| --- | --- |
| `GET /api/bootstrap` | ข้อมูลสาขา ภาคการศึกษา ประกาศ คำถามยอดนิยม (ไม่มีข้อมูลส่วนบุคคล) |
| `POST /api/session/face-confirm` | ผู้ใช้กด "ใช่" บนหน้ายืนยันตัวตน → ออกโทเค็นเซสชัน |
| `POST /api/session/student-id` | โหมดกรอกรหัส — ได้เซสชันแบบจำกัดข้อมูล |
| `POST /api/session/anonymous` | ใช้งานแบบไม่ระบุตัวตน |
| `GET /api/me/schedule` | ตารางวันนี้ · ทั้งสัปดาห์ · คาบถัดไป · นับถอยหลัง |
| `GET /api/me/exams` | กำหนดสอบ (มาจากรายวิชาที่ลงทะเบียน) |
| `DELETE /api/me/face` | ลบข้อมูลใบหน้าของตนเอง (ต้องยืนยันด้วยใบหน้าเท่านั้น) |
| `POST /api/assistant/ask` | ถามด้วย `questionId` (แตะ) หรือ `text` (พิมพ์) → คำตอบพร้อมแหล่งที่มา |
| `WS /ws/kiosk` | เหตุการณ์จากกล้อง ไมโครโฟน และเซ็นเซอร์ |

ทุกเส้นทางที่ขึ้นต้นด้วย `/api/me` ต้องส่งหัวข้อ `X-Kiosk-Session` และจะคืน 401 ถ้าไม่มีหรือหมดอายุ

## ข้อมูลจริง กับ ข้อมูลสมมติ

ตู้แยกสองอย่างนี้ออกจากกันอย่างชัดเจน และ**บอกผู้ใช้เสมอ**เมื่อสิ่งที่แสดงยังไม่ใช่ของจริง

| ข้อมูล | สถานะ | ที่มา |
| --- | --- | --- |
| ชื่อสาขา ที่ตั้ง เบอร์โทร อีเมล | จริง | เว็บไซต์สาขา |
| อาคาร 3 แห่ง · ห้องเรียน 9 ห้อง | จริง | เว็บไซต์สาขา |
| บุคลากร 15 คน (แสดง 10 คนที่เปิดเผยข้อมูลไว้) | จริง | เว็บไซต์สาขา |
| รายวิชา 253 วิชา | จริง | เว็บไซต์สาขา |
| ข่าว/ประกาศ 8 รายการ | จริง | เว็บไซต์สาขา |
| เอกสารสำหรับผู้ช่วย AI 352 ชิ้น | จริง | เว็บไซต์สาขา |
| **ตารางเรียนรายสัปดาห์** | **สมมติ** | สร้างบนห้องจริง+วิชาจริง `is_synthetic = 1` |
| **กำหนดสอบ** | **สมมติ** | เช่นเดียวกัน |
| **นักศึกษา 2 คน** | **สมมติ** | สำหรับสาธิตจนกว่าจะเชื่อมระบบทะเบียน |
| เวลาทำการสำนักงาน | **ไม่มีข้อมูล** | ไม่มีในเว็บไซต์ → ระบบไม่ตอบเรื่องเวลา |

ทุกแถวที่สมมติมีคอลัมน์ `is_synthetic = 1` และ `/api/bootstrap` คืนค่า `hasSyntheticSchedule`
หน้าจอจึงขึ้นป้าย **"ตารางเรียนเป็นข้อมูลตัวอย่าง ยังไม่ใช่ตารางจริง"** ทุกหน้าที่แสดงตารางเรียน

เมื่อได้ตารางเรียนจริงจากสาขา ให้เขียนสคริปต์นำเข้าโดยใช้โครงตารางเดิมและตั้ง `is_synthetic = 0`
ป้ายเตือนจะหายไปเอง ไม่ต้องแก้หน้าจอ

> **เวลาทำการสำนักงานเป็นตัวอย่างของกฎ "ห้ามเดาคำตอบ" ที่ใช้กับตัวเราเอง**
> ต้นแบบเดิมเคยแสดง "จันทร์–ศุกร์ 08.30–16.30 น." ซึ่งเป็นข้อความที่แต่งขึ้น
> ตอนนี้ช่องนี้เป็น `NULL` และระบบตอบเฉพาะที่ตั้งกับช่องทางติดต่อที่มีจริง
> ถ้าต้องการให้ตู้ตอบเรื่องเวลาทำการได้ ต้องขอข้อมูลจากสาขาแล้วกรอกเข้าฐานข้อมูล

## สถานะปัจจุบัน

**ทำแล้ว**

- หน้าจอครบ 11 หน้า ทำงานกับข้อมูลจากฐานข้อมูลทั้งหมด
- ฐานข้อมูล SQLite พร้อมกฎความเป็นส่วนตัวระดับ schema
- นำเข้าข้อมูลจริงของสาขาจาก `csmju_dataset` ครบทุกตาราง
- เซสชัน · การจำกัดข้อมูลตามวิธียืนยันตัวตน · ออกจากระบบอัตโนมัติ
- คำตอบจากฐานข้อมูล (ทำงานได้ขณะออฟไลน์) และผู้ช่วย AI พร้อม RAG บนเอกสารจริง 352 ชิ้น
- บันทึกสถิติการใช้งานแบบไม่มีข้อมูลระบุตัวตน
- โหมดจอคอมพิวเตอร์แนวนอน · หน้าต่างแชท · ถามด้วยการพิมพ์
- ชุดทดสอบ: API 37 ข้อ · ค้นเอกสาร 7 ข้อ · ตีความคำถาม 19 ข้อ · หน้าจอจริง ~41 ข้อ

- กล้องจริง · รู้จำใบหน้า · ลงทะเบียนใบหน้าพร้อมความยินยอม
- ถอดเสียงพูดภาษาไทยในเครื่อง และตอบคำถามปลายเปิดด้วย RAG

**ยังไม่ได้ทำ**

- **ตารางเรียนและกำหนดสอบจริง** — ยังไม่มีแหล่งข้อมูล (ไม่มีใน `csmju_dataset`)
- ยืนยันตัวตนตอนลงทะเบียนใบหน้าครั้งแรก (ต้องใช้กระบวนการของสาขา)
- เซ็นเซอร์ตรวจจับผู้ใช้แยกต่างหาก (ตอนนี้ใช้กล้องตรวจว่ามีคนอยู่หรือไม่)
- ทดสอบความเร็วจริงบน Raspberry Pi 5 (ตัวเลขข้างบนวัดจากโน้ตบุ๊ก)
- แดชบอร์ดผู้ดูแลระบบ
- ติดตั้งจริงบน Raspberry Pi (systemd + Chromium kiosk)

## ติดตั้งบน Raspberry Pi 5

```bash
# หน้าเว็บ
cd web && npm run build          # ได้ web/dist ซึ่งเซิร์ฟเวอร์จะเสิร์ฟให้เอง

# เซิร์ฟเวอร์
cd server
python3 -m venv .venv --system-site-packages
.venv/bin/pip install -r requirements.txt
.venv/bin/python -m app.seed
KIOSK_SIM=0 .venv/bin/python -m uvicorn app.main:app --host 127.0.0.1 --port 8000

# เบราว์เซอร์
chromium-browser --kiosk http://127.0.0.1:8000 \
  --noerrdialogs --disable-infobars --disable-pinch \
  --overscroll-history-navigation=0 --check-for-update-interval=31536000 \
  --use-fake-ui-for-media-stream    # อนุญาตไมโครโฟนอัตโนมัติ ไม่ต้องให้ผู้ใช้กดยอมรับ
```

เตรียมโมเดลไว้ก่อนเปิดใช้งานจริง แล้วตั้ง `KIOSK_STT_OFFLINE_ONLY=1`
เพื่อไม่ให้ตู้พยายามดาวน์โหลดโมเดลระหว่างให้บริการ

ตั้งจอเป็นแนวตั้ง 1080×1920 และปิด screen blanking ด้วย `xset s off -dpms`

หากตู้ต้องทำงานขณะออฟไลน์ ให้ดาวน์โหลดฟอนต์ IBM Plex Sans Thai และ Noto Sans Thai
มาเก็บไว้ในโปรเจกต์แทนการโหลดจาก Google Fonts ใน `web/index.html`
