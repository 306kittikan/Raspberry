# ตู้บริการข้อมูลอัจฉริยะ (Smart Kiosk)

ตู้บริการข้อมูลของ **สาขาวิชาวิทยาการคอมพิวเตอร์ คณะวิทยาศาสตร์ มหาวิทยาลัยแม่โจ้**
นักศึกษายืนหน้าตู้แล้วดูตารางเรียนของตนเองได้ทันที โดยไม่ต้องเข้าสู่ระบบหรือพิมพ์ข้อความ
พร้อมผู้ช่วยตอบคำถามเกี่ยวกับสาขาและอาคาร สั่งงานได้ทั้งการแตะและเสียง

ติดตั้งใช้งานบน Raspberry Pi 5 · จอสัมผัสแนวตั้ง 1080×1920 · Chromium kiosk mode

---

## หลักการออกแบบที่กำหนดทุกอย่างในโปรเจกต์นี้

**1. แยกประเภทคำถามก่อนตอบ**
คำถามที่มีคำตอบแน่นอน (ตารางเรียน ห้องเรียน กำหนดสอบ) ค้นจาก SQLite โดยตรง **ไม่ผ่าน AI**
จึงไม่มีโอกาสตอบผิด และยังทำงานได้เมื่ออินเทอร์เน็ตขัดข้อง
คำถามทั่วไปจึงส่งให้ผู้ช่วย AI ซึ่งถูกบังคับให้อ้างอิงเอกสารเสมอ

**2. ผู้ช่วย AI เขียนข้อความอ้างอิงเองไม่ได้**
โมเดลทำได้แค่เลือกหมายเลขชิ้นเอกสารที่ใช้ตอบ แล้วเซิร์ฟเวอร์ไปดึงชื่อเอกสารจากฐานข้อมูลมาแสดงเอง
ต่อให้โมเดลแต่งชื่อเอกสารขึ้นมา ก็ไม่มีทางหลุดออกหน้าจอ
ถ้าค้นเอกสารไม่เจอหรือเรียก API ไม่สำเร็จ ระบบตอบ "ไม่พบข้อมูลนี้ในระบบ" — ไม่เดาคำตอบ

**3. กฎความเป็นส่วนตัวบังคับที่ระดับฐานข้อมูล ไม่ใช่แค่ในโค้ด**
`face_embeddings.consent_id` เป็น `NOT NULL` + FK ไปยัง `consents`
เขียนเวกเตอร์ใบหน้าโดยไม่มีความยินยอมจึงทำไม่ได้เลย และการถอนความยินยอมลบเวกเตอร์ตามไปทันที
ไม่มีคอลัมน์ใดเก็บ "ภาพ" ใบหน้า และ `usage_events` ไม่มี FK ไป `students` โดยเจตนา

**4. หน้าเว็บบอกไม่ได้ว่า "ฉันคือใคร"**
บอกได้แค่ว่ากดยืนยันผู้ที่ระบบเสนอมา (candidateToken ใช้ได้ครั้งเดียว อายุ 45 วินาที)
รหัสนักศึกษาเต็มไม่เคยออกจากเซิร์ฟเวอร์ — ส่งเฉพาะรูปแบบปิดบัง `••••1001`

## เริ่มพัฒนา

ต้องมี **Python 3.11+** และ **Node.js 20+**

### 1. เซิร์ฟเวอร์

```bash
cd server
python -m venv .venv
.venv/Scripts/python.exe -m pip install -r requirements.txt   # Windows
# source .venv/bin/activate && pip install -r requirements.txt  # Linux/Pi

cp .env.example .env            # แก้ค่าตามต้องการ (ไม่ใส่ก็ใช้ค่าตั้งต้นได้)
.venv/Scripts/python.exe -m app.seed --reset       # นำเข้าข้อมูลจริง + สร้างตารางเรียนสาธิต
.venv/Scripts/python.exe -m uvicorn app.main:app --reload --port 8000
```

เปิดเอกสาร API อัตโนมัติได้ที่ http://127.0.0.1:8000/docs

### 2. หน้าจอ

```bash
cd web
npm install
npm run dev
```

เปิด http://localhost:5173 — Vite ส่งต่อ `/api` และ `/ws` ไปยังพอร์ต 8000 ให้เอง

### 3. ทดสอบ

```bash
cd server
.venv/Scripts/python.exe scripts/usecases.py          # กรณีการใช้งานทั้งหมด 93 ข้อ
.venv/Scripts/python.exe scripts/smoke.py             # API 37 ข้อ
.venv/Scripts/python.exe scripts/test_retrieval.py    # ค้นเอกสารภาษาไทย 7 ข้อ
.venv/Scripts/python.exe scripts/test_intent.py       # ตีความคำถามจากเสียง 19 ข้อ
.venv/Scripts/python.exe scripts/test_assistant_ai.py # ด่านกันการแต่งคำตอบ 30 ข้อ
.venv/Scripts/python.exe scripts/eval_retrieval.py    # วัดคุณภาพการค้นเอกสาร
.venv/Scripts/python.exe scripts/test_registry.py     # ทะเบียนและสิทธิเจ้าของข้อมูล 20 ข้อ
.venv/Scripts/python.exe scripts/test_roster.py       # อ่านและนำเข้ารายชื่อ 27 ข้อ
.venv/Scripts/python.exe scripts/test_face.py --check # ตรวจข้อมูลใบหน้าในระบบ

cd ../web && npm run e2e                              # ขับหน้าจอจริง ~37 ข้อ
```

ทั้งหมดนี้ไม่ต้องใช้กุญแจ API และไม่ต้องมีคนอยู่หน้ากล้อง

> จำนวนข้อของ `npm run e2e` เปลี่ยนตามสิ่งที่กล้องเห็นจริงในขณะนั้น
> ถ้ามีคนที่ลงทะเบียนใบหน้าไว้อยู่หน้าจอ ชุดทดสอบจะเดินเส้นทาง "จำได้ → ยืนยันตัวตน"
> ถ้าไม่มี จะเดินเส้นทาง "จำไม่ได้ → กรอกรหัสนักศึกษา" ทั้งสองทางถือว่าผ่าน

**ทดสอบกล้องด้วยตัวเอง** (ต้องนั่งอยู่หน้ากล้อง)

```bash
cd server
.venv/Scripts/python.exe scripts/test_face.py --enroll 6604101001   # ลงทะเบียนใบหน้าให้รหัสนี้
.venv/Scripts/python.exe scripts/test_face.py --recognize           # ดูคะแนนการจำแบบเรียลไทม์
```

`scripts/e2e.mjs` ใช้ Chrome/Edge/Chromium ที่ติดตั้งอยู่แล้วในเครื่อง ไม่ดาวน์โหลดเบราว์เซอร์เพิ่ม
เพิ่ม `--shots ./shots` เพื่อเก็บภาพหน้าจอทุกขั้น หรือ `--headed` เพื่อดูเบราว์เซอร์ทำงาน

## สองโหมดการแสดงผล

หน้าจอของตู้จริงเป็นแนวตั้ง 1080×1920 แต่ตอนพัฒนาบน Windows จอเป็นแนวนอน
ถ้าย่อทั้งเวทีให้พอดีความสูงจะเหลือเป็นแถบแคบ ๆ กลางจอดำ ใช้งานลำบาก

`Stage` จึงเลือกโหมดจากสัดส่วนหน้าจอเอง

| โหมด | เมื่อไหร่ | หน้าตา |
| --- | --- | --- |
| `kiosk` | จอสูงกว่ากว้าง (ตู้จริง) | เวที 1080×1920 ย่อให้พอดีทั้งจอ |
| `desktop` | จอกว้างกว่าสูง (Windows) | แผงคู่สนทนาซ้าย + หน้าจอตู้ขวา |

**ทั้งสองโหมดใช้หน้าจอชุดเดียวกัน** ขนาดตัวอักษรและเป้าแตะจึงยังตรงตามข้อกำหนดเสมอ
(เนื้อหา ≥ 24px · หัวข้อ ≥ 40px · เป้าแตะ ≥ 72×72px)
โหมด `desktop` แค่เอาพื้นที่ว่างด้านข้างมาใช้ประโยชน์ ไม่ได้แก้เนื้อหาข้างใน
จึงไม่มีทางที่หน้าจอบนตู้จริงกับบนเครื่องพัฒนาจะเพี้ยนไปคนละทาง

### แผงคู่สนทนา (PresencePanel)

แผงด้านซ้ายในโหมด `desktop` ทำหน้าที่เป็น "คู่สนทนา" ของนักศึกษา

- ภาพสดจากกล้อง **กลับด้านเหมือนส่องกระจก** เพราะผู้ใช้ขยับตัวตามภาพที่เห็น
- วงแหวนรอบภาพเปลี่ยนสีตามสถานะ: พร้อมฟัง / กำลังฟัง / กำลังคิด
- บทสนทนาเป็นบับเบิลสองฝั่ง — สิ่งที่ตู้ได้ยิน กับสิ่งที่ตู้ตอบ

บนตู้จริงไม่มีพื้นที่ด้านข้าง หน้าผู้ช่วยจึงแสดงภาพกล้องขนาดย่อข้างปุ่มไมโครโฟนแทน
เฉพาะตอนกำลังพูดคุย เพื่อให้รู้สึกเหมือนคุยกับใครสักคน ไม่ใช่พูดใส่ปุ่มเปล่า ๆ

## กล้อง ใบหน้า และเสียง

### กล้องเป็นของเซิร์ฟเวอร์ ไม่ใช่ของเบราว์เซอร์

การรู้จำใบหน้าทำงานฝั่ง Python อยู่แล้ว การส่งเฟรมวิดีโอจากเบราว์เซอร์มาประมวลผลจึงเสียเปล่า
และ Chromium โหมด kiosk บน Raspberry Pi ขออนุญาตใช้กล้องยุ่งยาก
หน้าเว็บจึงดูภาพสดผ่านสตรีม MJPEG ที่ `/api/face/stream` ซึ่งใส่ใน `<img>` ได้เลย

| ขั้นตอน | ทำอะไร |
| --- | --- |
| ตรวจจับ | SCRFD หาตำแหน่งใบหน้า (~4 ms บนโน้ตบุ๊ก · คาดว่า ~50–150 ms บน Pi 5) |
| แปลงเป็นเวกเตอร์ | ArcFace แปลงใบหน้าเป็นตัวเลข 512 มิติที่ normalise แล้ว |
| เทียบ | cosine similarity กับเวกเตอร์ที่ลงทะเบียนไว้ |

**กติกาการตัดสินว่า "ใช่คนนี้" ต้องผ่านสองด่าน**

1. คะแนนสูงกว่าเกณฑ์ (`KIOSK_FACE_THRESHOLD`, ค่าตั้งต้น 0.45)
2. ห่างจากอันดับสองอย่างน้อย `KIOSK_FACE_MARGIN` (ค่าตั้งต้น 0.05)

ด่านที่สองมีไว้แก้ความเสี่ยง **"ระบบรู้จำใบหน้าผิดคน"** ที่ระบุไว้ในเอกสารโดยตรง
เพราะการทักผิดคนแล้วแสดงตารางเรียนของคนอื่น คือการเปิดเผยข้อมูลส่วนบุคคล
ถ้าคะแนนอันดับ 1 กับ 2 ใกล้กันเกินไป ระบบจะตอบว่า "จำไม่ได้" แทนการเดา

### ลำดับการลงทะเบียนใบหน้า — ถ่ายก่อน กรอกรายละเอียดทีหลัง

```
จำใบหน้าไม่ได้ → "ลงทะเบียนใบหน้า" → ขอความยินยอม → ถ่าย 8 ใบ → กรอกรหัสนักศึกษา → เสร็จ
```

กล้องจ่ออยู่ที่หน้าผู้ใช้อยู่แล้ว การให้ถ่ายเลยจึงเป็นธรรมชาติกว่าการบังคับกรอกรหัสก่อน
และเวลาที่เสียไปกับการกรอกรหัส 10 หลักก็ไม่ต้องให้ยืนค้างอยู่หน้ากล้อง

| ขั้น | เกิดอะไรขึ้น |
| --- | --- |
| 1 · ยินยอม | แตะช่องยินยอมเอง (ห้ามติ๊กไว้ล่วงหน้า) เวลาที่กดถูกจำไว้ที่เซิร์ฟเวอร์ |
| 2 · ถ่าย | เก็บตัวอย่าง 8 ใบ เวกเตอร์ถูก**พักไว้ในหน่วยความจำ ยังไม่เขียนลงดิสก์** |
| 3 · กรอกรหัส | บอกว่าใบหน้านี้เป็นของรหัสใด แล้วบันทึกความยินยอม + เวกเตอร์พร้อมกันในรายการเดียว |

**ความยินยอมยังต้องมาก่อนการถ่ายเสมอ** เพราะ พ.ร.บ.คุ้มครองข้อมูลส่วนบุคคลฯ มาตรา 26
กำหนดไว้สำหรับข้อมูลชีวภาพ สิ่งที่ย้ายไปอยู่ท้ายสุดคือ "รหัสนักศึกษา" ไม่ใช่ความยินยอม

ผลพลอยได้ด้านความปลอดภัย: **ไม่มีเวกเตอร์ใบหน้าแตะดิสก์เลย จนกว่าจะมีความยินยอมผูกกับตัวบุคคล**
ถ้าผู้ใช้เดินจากไปกลางคัน ข้อมูลที่พักไว้หมดอายุใน 3 นาทีแล้วหายไปเอง

ถ้ายืนยันตัวตนอยู่แล้ว (กดลงทะเบียนจากหน้าหลัก) จะข้ามขั้นกรอกรหัส เพราะเซิร์ฟเวอร์รู้จากเซสชันแล้ว

ครั้งถัดไปนักศึกษายืนหน้าตู้แล้วระบบจำได้ทันที ไม่ต้องกรอกรหัสอีก

### เก็บอะไรบ้างตอนลงทะเบียนใบหน้า

เก็บเวกเตอร์ 512 มิติที่เฉลี่ยจากตัวอย่าง 8 ใบเท่านั้น **ไม่มีการบันทึกภาพหรือวิดีโอ**
ก่อนบันทึกระบบตรวจสองอย่าง

- ตัวอย่างทั้ง 8 ใบต้องสอดคล้องกันไม่น้อยกว่า 0.60 ไม่งั้นให้ถ่ายใหม่
- เวกเตอร์ที่ได้ต้องไม่ตรงกับผู้ที่ลงทะเบียนไว้แล้ว มิฉะนั้นปฏิเสธ

> ⚠️ **ช่องโหว่ที่ยังเหลืออยู่ และต้องแก้ด้วยกระบวนการ ไม่ใช่โค้ด**
> การลงทะเบียนใช้การกรอกรหัสนักศึกษาเป็นตัวระบุตัวตน ซึ่งไม่ได้ยืนยันว่าเป็นเจ้าของรหัสจริง
> ระบบจึงกันไว้ว่า **รหัสที่มีข้อมูลใบหน้าอยู่แล้วลงทะเบียนซ้ำไม่ได้** (HTTP 409)
> ผู้ที่ต้องการลงทะเบียนใหม่ต้องไปลบข้อมูลเดิมที่สำนักงานสาขาก่อน
> การแก้ให้สมบูรณ์คือให้เจ้าหน้าที่ยืนยันตัวตนตอนลงทะเบียนครั้งแรก

### เสียงพูดภาษาไทย

ใช้ **faster-whisper** ทำงานบนเครื่องของตู้เอง ไม่ต้องต่ออินเทอร์เน็ต
ไม่ใช้ Web Speech API ของเบราว์เซอร์ เพราะ Chromium บน Raspberry Pi ไม่มีบริการรู้จำเสียงให้ใช้
ถ้าพึ่งมันแล้วย้ายไปลงตู้จริง ฟีเจอร์เสียงจะใช้ไม่ได้ทันที

| | |
| --- | --- |
| อัดเสียง | เบราว์เซอร์ใช้ `MediaRecorder` (webm/opus) ส่งผ่าน `/ws/voice` |
| ถอดรหัส | PyAV ที่ติดมากับ faster-whisper — ไม่ต้องลง ffmpeg และไม่ต้องเขียน AudioWorklet |
| ถอดความ | รุ่น `base` int8 · ~0.5–1.5 วิ บนโน้ตบุ๊ก · คาดว่า ~2–5 วิ บน Pi 5 |
| ตีความคำถาม | คำสำคัญก่อน แล้วค่อยวัดความคล้ายตัวอักษร (`app/services/intent.py`) |

**ไม่มีการบันทึกไฟล์เสียงลงดิสก์** เสียงอยู่ในหน่วยความจำจนถอดความเสร็จแล้วถูกทิ้ง
และไม่มีการเก็บข้อความที่ถอดได้ลงฐานข้อมูล สถิติที่บันทึกมีแค่ประเภทคำถาม ช่องทาง และแหล่งคำตอบ
เหมือนตอนแตะปุ่มทุกประการ

### ถ้าถอดเสียงเพี้ยน

ความแม่นขึ้นกับสามอย่าง เรียงตามผลที่ได้จากมากไปน้อย

| ปรับอะไร | ที่ไหน | ผล |
| --- | --- | --- |
| รุ่นโมเดล | `KIOSK_STT_MODEL` | `base` เร็วแต่เพี้ยนบ่อย · **`small` เป็นค่าปริยาย** · `medium` แม่นสุดแต่ช้า |
| ความกว้างการค้นหา | `KIOSK_STT_BEAM` | 1 เร็วสุด · **5 แม่นสุด** |
| บริบทคำเฉพาะ | `KIOSK_STT_VOCAB` | ช่วยกับชื่ออาจารย์ แต่เมื่อเสียงไม่ชัดอาจพ่นคำพวกนี้ออกมาแทน |

ภาษาไทยมีสัดส่วนน้อยในข้อมูลที่ใช้ฝึก Whisper รุ่นเล็กจึงเพี้ยนกว่าภาษาอังกฤษมาก
`small` กินหน่วยความจำราว 250 MB มากกว่า `base` ราวสามเท่า
ถ้าตู้จริงบนหน่วยความจำจำกัดโหลดไม่ไหว ให้ลดกลับเป็น `base`

ฝั่งเบราว์เซอร์ก็มีผล ตอนนี้ขออัดที่ 48 kHz ช่องเดียว 128 kbps
และ**ปิด**การตัดเสียงรบกวนกับการปรับระดับเสียงอัตโนมัติของเบราว์เซอร์
สองตัวนี้ออกแบบมาให้คนฟังสบายหู ไม่ได้ออกแบบมาให้เครื่องถอดความ
การตัดเสียงรบกวนกินเสียงพยัญชนะเบา ๆ อย่าง ส ฉ ถ ซึ่งเป็นสิ่งที่ใช้แยกคำ
ส่วนการปรับระดับเสียงอัตโนมัติดึงเสียงพื้นหลังขึ้นมาตอนคนหยุดพูด
ยังเปิดการตัดเสียงสะท้อนไว้ เพราะตู้ใช้ลำโพง ไม่ใช่หูฟัง

---

การถอดเสียงทำในเครื่อง จึง**พูดถามตารางเรียนได้แม้ตู้ออฟไลน์** มีเพียงคำถามที่ต้องใช้ผู้ช่วย AI
เท่านั้นที่ถูกปิดตอนไม่มีอินเทอร์เน็ต

คำถามที่ระบบจับคู่กับปุ่มไม่ได้ จะถูกส่งให้ผู้ช่วย AI ค้นเอกสารของสาขาตอบ
โดยยังต้องอ้างอิงเอกสารเสมอตามกติกาเดิม ถ้าค้นไม่เจอจะได้ "ไม่พบข้อมูลนี้ในระบบ"

### ตารางเรียนจริงรายบุคคล

ตั้งแต่เริ่มโครงงาน ตารางเรียนบนหน้าจอเป็นข้อมูลสมมติมาตลอด เพราะสาขายังไม่มี
ช่องทางส่งตารางเรียนจริงมาให้ หน้าจอจึงต้องติดป้ายเตือนว่า "ตารางเรียนเป็นข้อมูลตัวอย่าง"

ตอนนี้มีของจริงแล้ว โดยนักศึกษาดึงจากระบบทะเบียนของตัวเอง

```bash
cd server
.venv/Scripts/python.exe scripts/import_my_semester.py <โฟลเดอร์> --dry-run
.venv/Scripts/python.exe scripts/import_my_semester.py ../csmju_dataset/my_semester_1-2569
```

ระบบทะเบียนกับเว็บไซต์สาขาเรียกห้องเดียวกันคนละชื่อ (`Lab คอม 5` กับ `Labcom 5`)
จึงต้องมีตารางแมปไว้ ไม่งั้นตู้จะสร้างห้องซ้ำแล้วบอกชั้นกับอาคารไม่ได้

ห้องของคณะอื่นไม่มีในฐานข้อมูลของสาขา เพราะสาขาเก็บเฉพาะห้องของตัวเอง
กรณีนั้นบันทึกแค่ชื่อห้องไว้ แล้วหน้าจอไม่แสดงชั้นและอาคาร
**ไม่เดาเลขชั้นขึ้นมาเอง** เพราะจะทำให้นักศึกษาเดินขึ้นผิดชั้น

### เมื่อข้อมูลต้นทางผิด

ชุดข้อมูลของสาขาระบุว่า `Lect 8` อยู่ชั้น 2 แต่นักศึกษาที่เรียนห้องนั้นยืนยันว่าชั้น 6
ตู้บอกทางไปห้องเรียน **การบอกชั้นผิดแปลว่านักศึกษาเดินขึ้นผิดชั้นแล้วเข้าเรียนสาย**

ถ้าค้นรวมกันหมด คำถาม "ขอใบรับรองทำยังไง" จะได้เอกสารการเงินของเจ้าหน้าที่
จึงทำเครื่องหมาย `for_students` ไว้ตั้งแต่ตอนนำเข้า เหลือ 78 ฉบับที่นักศึกษาใช้จริง

ป้ายอ้างอิงของชิ้นเอกสารกลุ่มนี้บอกว่ามาจาก **สำนักบริหารและพัฒนาวิชาการ**
ไม่ใช่เว็บไซต์ของสาขา เพราะเป็นคนละแหล่ง ถ้าบอกผิดนักศึกษาจะตามกลับไปหาต้นทางไม่ถูก

### ตู้คาดการณ์ว่าช่วงนี้จะถูกถามอะไร

ปุ่มคำถามยอดนิยมตั้งไว้ตายตัว จึงเสนอเรื่องเดิมทั้งปี ทั้งที่สิ่งที่นักศึกษากังวล
เปลี่ยนไปตามช่วงของเทอม ก่อนสอบทุกคนถามเรื่องห้องสอบ ต้นเทอมถามเรื่องลงทะเบียน

ตอนนี้หน้าแชทมีหัวข้อ **"ช่วงนี้น่าจะถาม"** อยู่บนสุด ซึ่งดูจากปฏิทินการศึกษาจริง
ว่าเหตุการณ์ใดกำลังจะถึง แล้วเสนอคำถามที่เกี่ยวข้องก่อน พร้อมบอกเหตุผลกำกับ

```
ตารางสอบปลายภาคสอบวันไหนบ้าง
  วันสอบปลายภาค (งดการเรียนการสอน) · อีก 22 วัน

ขั้นตอนการลงทะเบียนออนไลน์ทำอย่างไร
  วันลงทะเบียนรายวิชา นักศึกษารหัส 69 · 11 พฤศจิกายน 2569
```

ไม่ได้เดาจากสถิติการใช้งาน เพราะตู้ยังไม่มีข้อมูลมากพอ และการเดาจากสถิติ
ทำให้คำถามที่ไม่เคยมีใครถามไม่มีวันถูกเสนอ ทั้งที่อาจสำคัญที่สุดในสัปดาห์นั้น

### ถามเจาะลึกลงไปในชุดข้อมูลได้

คำถามที่มีคำตอบแน่นอนในฐานข้อมูล **ไม่ถูกส่งให้ AI เดา** แม้จะเป็นคำถามปลายเปิด

| ถามว่า | ตอบจาก | ได้อะไร |
| --- | --- | --- |
| `อีเมลอาจารย์พาสน์คืออะไร` | ตารางบุคลากร | ชื่อ ตำแหน่ง อีเมล เบอร์ต่อ วุฒิการศึกษา ความเชี่ยวชาญ |
| `ใครสอนเรื่อง IoT` | ตารางบุคลากร | **ครบทุกคน** ที่มีหัวข้อนั้นในความเชี่ยวชาญ |
| `อยากปรึกษาเรื่องฐานข้อมูล ถามใครดี` | ตารางบุคลากร | รายชื่อพร้อมอีเมล |
| `อาจารย์คนไหนเก่งที่สุด` | ผู้ช่วย AI | ไม่มีคำตอบในเอกสาร → ไม่เดา |

สองแบบแรกตอบได้**แม้ตู้ออฟไลน์** และไม่มีทางผิด เพราะอ่านจากตารางตรง ๆ

การให้ AI อ่านเอกสารแทนจะได้คำตอบที่ขาดคนไป เพราะโมเดลเห็นเฉพาะชิ้นที่ค้นมาให้
และอ้างอิงได้ทีละชิ้น คำถามอย่าง "ใครสอนเรื่อง IoT" จึงเคยตอบมาแค่คนเดียว
ทั้งที่ในฐานข้อมูลมีสามคน

ฐานข้อมูลเก็บความเชี่ยวชาญเป็นภาษาอังกฤษเต็มรูป เช่น `Internet of Things`
แต่ไม่มีนักศึกษาคนไหนพูดแบบนั้น `repo.TOPIC_ALIASES` จึงแปลงคำย่อและคำไทย
(IoT, ไอโอที, เอไอ, เหมืองข้อมูล, บล็อกเชน) ให้ตรงกับที่เก็บไว้

เฉพาะบุคลากรที่ระบบต้นทางกำหนดให้เปิดเผยได้เท่านั้น (10 จาก 15 คน)
ตู้ตั้งในที่สาธารณะและคนเดินผ่านมองเห็นจอ

การสลับผู้ให้บริการแตะได้แค่ `app/services/llm.py` เท่านั้น
**ด่านกันการแต่งคำตอบไม่ถูกแตะเลยแม้แต่บรรทัดเดียว** ซึ่งเป็นเจตนาของการแยกชั้นนี้
เพราะด่านเหล่านั้นคือสิ่งที่กันไม่ให้คำตอบผิดขึ้นจอ และต้องทำงานเหมือนกันทุกราย

> **ข้อควรรู้ก่อนใช้โควตาฟรีกับตู้จริง**
>
> โควตาฟรีของ Gemini มีเงื่อนไขว่าผู้ให้บริการนำเนื้อหาที่ส่งไปใช้ปรับปรุงบริการได้
> ต่างจากแบบเสียเงินซึ่งไม่นำไปใช้ — ควรอ่านเงื่อนไขล่าสุดก่อนเปิดใช้กับผู้ใช้จริง
>
> สิ่งที่ถูกส่งออกไปมีเพียง **ข้อความคำถาม** กับ **เอกสารของสาขา** เท่านั้น
> ไม่มีรหัสนักศึกษา ชื่อ ตารางเรียน หรือข้อมูลใบหน้าออกไปด้วยเลย
> เพราะคำถามที่ต้องใช้ข้อมูลส่วนบุคคลถูกตอบจากฐานข้อมูลในเครื่องก่อนเสมอ
>
> ความเสี่ยงที่เหลือคือนักศึกษาพิมพ์หรือพูดข้อมูลส่วนตัวลงในคำถามเอง
> ถ้าจะใช้กับผู้ใช้จริงในวงกว้าง ควรใช้แบบเสียเงินหรือแจ้งผู้ใช้ให้ชัดที่หน้าจอ

```bash
curl http://127.0.0.1:8000/api/ai/status
```

```json
{"enabled": true, "provider": "gemini", "model": "gemini-3.1-flash-lite",
 "calls": 5, "failures": 0, "lastError": null, "inputTokens": 13977}
```

เส้นทางนี้บอกว่าผู้ช่วย **ใช้งานได้จริง** หรือไม่ ต่างจาก `aiEnabled` ใน `/api/health`
ซึ่งบอกเพียงว่าตั้งค่ากุญแจไว้แล้ว กุญแจที่หมดอายุหรือเครดิตที่หมดจะทำให้ตู้ตอบ
"ไม่พบข้อมูลนี้ในระบบ" ทุกคำถามโดยไม่มีอะไรบนจอบอกสาเหตุ
`lastError` จึงเก็บรหัสไว้ (`auth`, `rate_limit`, `unavailable`, `connection`, `refusal`)
รหัสเหล่านี้เหมือนกันทุกผู้ให้บริการ เพราะเจ้าหน้าที่สนใจว่า "กุญแจมีปัญหา"
หรือ "เน็ตมีปัญหา" ไม่ได้สนใจว่าใครเป็นคนแจ้ง
พร้อมจำนวนโทเค็นสะสมไว้ประเมินค่าใช้จ่ายจากตัวเลขจริง
ไม่มีเนื้อหาคำถามหรือข้อมูลส่วนบุคคลอยู่ในนั้น

| --- | --- |

| เรียกไม่สำเร็จ (กุญแจ/เน็ต/โควตา) | ตอบว่าไม่พบข้อมูล พร้อมช่องทางติดต่อ |

ด่านเหล่านี้คือสิ่งเดียวที่กันไม่ให้คำตอบที่แต่งขึ้นไปอยู่บนจอ
และความผิดพลาดแบบนี้จะไม่มีใครสังเกตเห็นจนกว่าจะมีนักศึกษาเดินไปผิดตึกแล้ว

## ทะเบียนนักศึกษาและสิทธิของเจ้าของข้อมูล

### นำเข้ารายชื่อนักศึกษา

นักศึกษาจะลงทะเบียนใบหน้าได้ก็ต่อเมื่อรหัสของตนอยู่ในระบบแล้ว
**ตู้ไม่รับสมัครคนใหม่เอง** เพราะการกรอกรหัสที่หน้าตู้ไม่ได้ยืนยันว่าเป็นเจ้าของรหัสจริง
ถ้าปล่อยให้สร้างรายชื่อได้เอง ใครก็จองรหัสของผู้อื่นไว้ล่วงหน้าได้

```bash
cd server
.venv/Scripts/python.exe scripts/import_students.py --template รายชื่อ.csv  # สร้างไฟล์ตัวอย่าง
.venv/Scripts/python.exe scripts/import_students.py รายชื่อ.csv --dry-run   # ตรวจไฟล์ก่อน
.venv/Scripts/python.exe scripts/import_students.py รายชื่อ.csv             # นำเข้าจริง
```

ไฟล์เป็น CSV (UTF-8) คอลัมน์ `student_id,name,year,program,advisor`
โดย `student_id` กับ `name` จำเป็น ที่เหลือเว้นว่างได้

สคริปต์แยก **"ข้าม"** (นำเข้าคนนี้ไม่ได้เลย) ออกจาก **"เตือน"** (นำเข้าได้แต่บางช่องใช้ไม่ได้)
เจ้าหน้าที่จึงรู้ทันทีว่ามีใครตกหล่นไปหรือไม่

การนำเข้า**ไม่ลบใครออกจากระบบ** เพราะการลบนักศึกษาจะลบเวกเตอร์ใบหน้าตามไปด้วย
ซึ่งต้องเป็นการตัดสินใจของคน ไม่ใช่ผลข้างเคียงของการนำเข้าไฟล์

### จัดการทะเบียนและข้อมูลใบหน้า

```bash
.venv/Scripts/python.exe scripts/students.py --list               # นักศึกษาทั้งหมด
.venv/Scripts/python.exe scripts/students.py --registry           # ใครลงทะเบียนใบหน้าแล้วบ้าง
.venv/Scripts/python.exe scripts/students.py --show 6604101388    # ข้อมูลทั้งหมดของคนหนึ่งคน
.venv/Scripts/python.exe scripts/students.py --export 6604101388 --out ของฉัน.json
.venv/Scripts/python.exe scripts/students.py --forget 6604101388  # ลบข้อมูลใบหน้า
.venv/Scripts/python.exe scripts/students.py --cleanup-consents   # ล้างความยินยอมที่ค้าง
```

> **ทำไมต้องมี `--forget` ทั้งที่ตู้มีปุ่มลบอยู่แล้ว**
>
> การลบผ่านหน้าตู้ต้องยืนยันตัวตนด้วยใบหน้าก่อน ถ้าระบบจำหน้าเจ้าของข้อมูลไม่ได้
> (เปลี่ยนทรงผม ใส่แว่น กล้องเสีย) เจ้าของข้อมูลจะลบข้อมูลตัวเองไม่ได้เลย
> ซึ่งขัดกับสิทธิที่กฎหมายรับรองไว้ จึงต้องมีช่องทางให้เจ้าหน้าที่ทำแทนเมื่อมีผู้มาติดต่อ
>
> หน้าจัดการข้อมูลใบหน้าบนตู้บอกทางออกนี้ไว้ด้วย เมื่อผู้ใช้กดลบไม่ได้

เครื่องมือทั้งสองตั้งใจให้รันบนเครื่องตู้โดยตรง (ผ่าน SSH) **ไม่ได้เปิดเป็น API**
เพราะยังไม่มีระบบยืนยันตัวตนของเจ้าหน้าที่ การเปิดเป็นเส้นทางเว็บโดยไม่มีการยืนยัน
จะกลายเป็นช่องให้ใครก็ได้ลบข้อมูลใบหน้าของผู้อื่น (แดชบอร์ดผู้ดูแลจะทำแยกภายหลัง)

### ความยินยอมที่ค้าง

ผู้ใช้ที่กดยินยอมแล้วเดินจากไปก่อนถ่ายเสร็จ จะทิ้งบันทึกความยินยอมไว้โดยไม่มีข้อมูลใดผูกอยู่
ปล่อยไว้ไม่ได้ เพราะเป็นหลักฐานว่า "ผู้นี้ยินยอมให้เก็บข้อมูลชีวภาพ" ทั้งที่ระบบไม่ได้เก็บอะไรจริง

`--registry` แสดงรายการเหล่านี้ให้เห็น และ `--cleanup-consents` ถอนทิ้งได้

> ลำดับการลงทะเบียนแบบใหม่ (ยินยอม → ถ่าย → กรอกรหัส) บันทึกความยินยอมพร้อมเวกเตอร์
> ในรายการเดียวตอนจบ จึงไม่สร้างรายการค้างอีกแล้ว คำสั่งนี้ใช้ล้างของเก่าที่ตกค้างมา

## ปรับโครงฐานข้อมูลของตู้ที่ติดตั้งไปแล้ว

`schema.sql` ใช้ `CREATE TABLE IF NOT EXISTS` จึงสร้างตารางใหม่ได้อย่างเดียว
แก้ตารางที่มีอยู่แล้วไม่ได้ `app/migrations.py` รับหน้าที่นั้น และถูกเรียกทุกครั้งที่เริ่มเซิร์ฟเวอร์

ทุกขั้นตอนต้องเรียกซ้ำได้โดยไม่เกิดผลข้างเคียง เพราะตู้ที่ให้บริการแล้วมีเวกเตอร์ใบหน้า
และบันทึกความยินยอมอยู่ ซึ่งลบทิ้งไม่ได้ — ผู้ใช้จะต้องมาลงทะเบียนใหม่ทั้งหมด

## แผงตัวควบคุมทดสอบ

แตะแถบเล็ก ๆ ที่ **ขอบขวาของจอ (กึ่งกลางแนวตั้ง)** เพื่อเปิดแผงจำลองสถานะ

| กลุ่ม | ปุ่ม |
| --- | --- |
| เซ็นเซอร์ | ตรวจพบคน (ปลุกจอ) · เข้าสู่จอพักลึก |
| ใบหน้า | จำหน้าได้ · จำหน้าไม่ได้ · พบหลายใบหน้า · หาใบหน้าไม่เจอ · กล้องใช้งานไม่ได้ · สลับผู้ใช้ |
| เครือข่าย | ออนไลน์ · ออฟไลน์ |
| เสียง | กำลังฟังเสียง · ฟังไม่ชัด |
| ข้อมูล | ไม่มีข้อมูลตารางเรียน · รีเซ็ตทั้งหมด |

ปุ่มเหล่านี้ไม่ได้เปลี่ยนสถานะในหน้าเว็บโดยตรง แต่ยิงไปที่ `/api/sim/*`
แล้วเซิร์ฟเวอร์ผลักเหตุการณ์กลับมาทาง WebSocket **เส้นทางเดียวกับที่กล้องจริงจะใช้**
เมื่อกล้องมาถึงจึงเปลี่ยนแค่ผู้ผลิตเหตุการณ์ ไม่ต้องแก้หน้าจอ

> ⚠️ ตั้ง `KIOSK_SIM=0` เมื่อติดตั้งบนตู้จริง มิฉะนั้นใครก็ยิง `/api/sim/face/recognized`
> เพื่อสวมรอยเป็นนักศึกษาคนใดก็ได้

## API

| เส้นทาง | หน้าที่ |
| --- | --- |
| `GET /api/bootstrap` | ข้อมูลสาขา ภาคการศึกษา ประกาศ คำถามยอดนิยม (ไม่มีข้อมูลส่วนบุคคล) |
| `POST /api/session/face-confirm` | ผู้ใช้กด "ใช่" บนหน้ายืนยันตัวตน → ออกโทเค็นเซสชัน |
| `POST /api/session/student-id` | โหมดกรอกรหัส — ได้เซสชันแบบจำกัดข้อมูล |
| `POST /api/session/anonymous` | ใช้งานแบบไม่ระบุตัวตน |
| `GET /api/me/schedule` | ตารางวันนี้ · ทั้งสัปดาห์ · คาบถัดไป · นับถอยหลัง |
| `GET /api/me/exams` | กำหนดสอบ (มาจากรายวิชาที่ลงทะเบียน) |
| `DELETE /api/me/face` | ลบข้อมูลใบหน้าของตนเอง (ต้องยืนยันด้วยใบหน้าเท่านั้น) |
| `POST /api/assistant/ask` | ถามด้วย `questionId` (แตะ) หรือ `text` (พิมพ์) → คำตอบพร้อมแหล่งที่มา |
| `WS /ws/kiosk` | เหตุการณ์จากกล้อง ไมโครโฟน และเซ็นเซอร์ |

ทุกเส้นทางที่ขึ้นต้นด้วย `/api/me` ต้องส่งหัวข้อ `X-Kiosk-Session` และจะคืน 401 ถ้าไม่มีหรือหมดอายุ

## ข้อมูลจริง กับ ข้อมูลสมมติ

ตู้แยกสองอย่างนี้ออกจากกันอย่างชัดเจน และ**บอกผู้ใช้เสมอ**เมื่อสิ่งที่แสดงยังไม่ใช่ของจริง

| ข้อมูล | สถานะ | ที่มา |
| --- | --- | --- |
| ชื่อสาขา ที่ตั้ง เบอร์โทร อีเมล | จริง | เว็บไซต์สาขา |
| อาคาร 3 แห่ง · ห้องเรียน 9 ห้อง | จริง | เว็บไซต์สาขา |
| บุคลากร 15 คน (แสดง 10 คนที่เปิดเผยข้อมูลไว้) | จริง | เว็บไซต์สาขา |
| รายวิชา 253 วิชา | จริง | เว็บไซต์สาขา |
| ข่าว/ประกาศ 8 รายการ | จริง | เว็บไซต์สาขา |
| เอกสารสำหรับผู้ช่วย AI 549 ชิ้น | จริง | เว็บไซต์สาขา + สำนักบริหารฯ |
| ตารางสอบปลายภาค 1/2569 306 รายการ | จริง | สำนักบริหารและพัฒนาวิชาการ |
| ปฏิทินการศึกษา 2569 48 รายการ | จริง | สำนักบริหารและพัฒนาวิชาการ |
| **ตารางเรียนรายสัปดาห์** | **สมมติ** | สร้างบนห้องจริง+วิชาจริง `is_synthetic = 1` |
| **กำหนดสอบ** | **สมมติ** | เช่นเดียวกัน |
| **นักศึกษา 2 คน** | **สมมติ** | สำหรับสาธิตจนกว่าจะเชื่อมระบบทะเบียน |
| เวลาทำการสำนักงาน | **ไม่มีข้อมูล** | ไม่มีในเว็บไซต์ → ระบบไม่ตอบเรื่องเวลา |

ทุกแถวที่สมมติมีคอลัมน์ `is_synthetic = 1` และ `/api/bootstrap` คืนค่า `hasSyntheticSchedule`
หน้าจอจึงขึ้นป้าย **"ตารางเรียนเป็นข้อมูลตัวอย่าง ยังไม่ใช่ตารางจริง"** ทุกหน้าที่แสดงตารางเรียน

เมื่อได้ตารางเรียนจริงจากสาขา ให้เขียนสคริปต์นำเข้าโดยใช้โครงตารางเดิมและตั้ง `is_synthetic = 0`
ป้ายเตือนจะหายไปเอง ไม่ต้องแก้หน้าจอ

> **เวลาทำการสำนักงานเป็นตัวอย่างของกฎ "ห้ามเดาคำตอบ" ที่ใช้กับตัวเราเอง**
> ต้นแบบเดิมเคยแสดง "จันทร์–ศุกร์ 08.30–16.30 น." ซึ่งเป็นข้อความที่แต่งขึ้น
> ตอนนี้ช่องนี้เป็น `NULL` และระบบตอบเฉพาะที่ตั้งกับช่องทางติดต่อที่มีจริง
> ถ้าต้องการให้ตู้ตอบเรื่องเวลาทำการได้ ต้องขอข้อมูลจากสาขาแล้วกรอกเข้าฐานข้อมูล

## สถานะปัจจุบัน

**ทำแล้ว**

- หน้าจอครบ 11 หน้า ทำงานกับข้อมูลจากฐานข้อมูลทั้งหมด
- ฐานข้อมูล SQLite พร้อมกฎความเป็นส่วนตัวระดับ schema
- นำเข้าข้อมูลจริงของสาขาจาก `csmju_dataset` ครบทุกตาราง
- เซสชัน · การจำกัดข้อมูลตามวิธียืนยันตัวตน · ออกจากระบบอัตโนมัติ
- คำตอบจากฐานข้อมูล (ทำงานได้ขณะออฟไลน์) และผู้ช่วย AI พร้อม RAG บนเอกสารจริง 352 ชิ้น
- บันทึกสถิติการใช้งานแบบไม่มีข้อมูลระบุตัวตน
- โหมดจอคอมพิวเตอร์แนวนอน · หน้าต่างแชท · ถามด้วยการพิมพ์
- นำเข้ารายชื่อนักศึกษา · ทะเบียนผู้ลงทะเบียนใบหน้า · เครื่องมือจัดการสิทธิเจ้าของข้อมูล
- ชุดทดสอบรวม ~280 ข้อ: กรณีการใช้งาน 98 · API 37 · ด่านกันการแต่งคำตอบ 37 ·
  ค้นเอกสาร 7 · ตีความคำถาม 19 · ทะเบียน 20 · รายชื่อ 27 · หน้าจอจริง ~37
- คุณภาพการค้นเอกสาร recall@5 90% วัดจากคำถาม 39 ข้อแบบที่นักศึกษาถามจริง

- กล้องจริง · รู้จำใบหน้า · ลงทะเบียนใบหน้าพร้อมความยินยอม
- ถอดเสียงพูดภาษาไทยในเครื่อง และตอบคำถามปลายเปิดด้วย RAG

**ยังไม่ได้ทำ**

- **ตารางเรียนและกำหนดสอบจริง** — ยังไม่มีแหล่งข้อมูล (ไม่มีใน `csmju_dataset`)
- ยืนยันตัวตนตอนลงทะเบียนใบหน้าครั้งแรก (ต้องใช้กระบวนการของสาขา)
- เซ็นเซอร์ตรวจจับผู้ใช้แยกต่างหาก (ตอนนี้ใช้กล้องตรวจว่ามีคนอยู่หรือไม่)
- ทดสอบความเร็วจริงบน Raspberry Pi 5 (ตัวเลขข้างบนวัดจากโน้ตบุ๊ก)
- แดชบอร์ดผู้ดูแลระบบ
- ติดตั้งจริงบน Raspberry Pi (systemd + Chromium kiosk)

## ภาษาของงานออกแบบ

หน้าจอใช้ **พื้นผิวที่ลอยขึ้นมา** ไม่ใช่กล่องที่วาดด้วยเส้น

เดิมทุกอย่างมีกรอบหนา 2px ซึ่งทำให้หน้าจอดูเป็นแผนผังมากกว่าเป็นของที่จับต้องได้
ตอนนี้ใช้เส้นขอบบางระดับเส้นผมบวกเงาสองชั้นแทน (`shadow-card` · `shadow-hero`)
พื้นหลังเป็นไล่สีอ่อน ๆ (`.stage-surface`) การ์ดสีขาวจึงแยกตัวออกมาได้เอง

| เดิม | ตอนนี้ |
| --- | --- |
| กรอบ 2px ทุกชิ้น | เส้นขอบ 1px + เงานุ่ม |
| พื้นขาวล้วน | ไล่สีเขียวอ่อนมาก |
| ปุ่มสีทึบ | ไล่สีบนลงล่าง + เงายกขึ้น |
| แท็บสามปุ่มแยกกรอบ | รางเดียวมีปุ่มเลื่อนข้างใน (`.segment`) |
| ส่วนหัวเขียวทึบตัดตรง | ไล่สีทแยง มุมล่างโค้ง มีแสงฟุ้ง |

### ข้อจำกัดที่กำหนดว่าทำอะไรได้บ้าง

ตู้รันบน Raspberry Pi 5 เทคนิคที่สวยแต่กินแรงเครื่องจึงใช้ไม่ได้

- **ไม่ใช้ `backdrop-filter`** — การเบลอพื้นหลังกิน GPU มากบน Pi
  แสงฟุ้งในส่วนหัวใช้ไล่สีแบบรัศมีแทน ซึ่งได้ผลใกล้เคียงและแทบไม่กินแรง
- **ไม่ใส่เงาในรายการที่ซ้ำหลายสิบแถว** — แถวรายวิชาใช้ `ring-1` แทน `shadow`
  เงาจำนวนมากทำให้การเลื่อนหน้าจอกระตุก
- **แอนิเมชันใช้ `transform` กับ `opacity` เท่านั้น** — สองอย่างนี้ทำงานบน GPU
  ส่วนการขยับ `width` หรือ `top` บังคับให้เบราว์เซอร์คำนวณผังหน้าใหม่ทุกเฟรม

ขนาดตัวอักษรและเป้าแตะไม่ได้เล็กลงเลย เพราะผู้ใช้ยืนอ่านจากระยะ 50–80 ซม.
ความทันสมัยในที่นี้คือความลึกและพื้นผิว ไม่ใช่ความหนาแน่น

## ติดตั้งบน Raspberry Pi 5

ขั้นตอนเต็มอยู่ที่ **[docs/deploy-raspberry-pi.md](docs/deploy-raspberry-pi.md)**
ตั้งแต่เครื่องเปล่าจนเปิดให้บริการ พร้อมรายการตรวจก่อนส่งมอบและวิธีแก้ปัญหาที่พบบ่อย

ย่อสุด ๆ

```bash
# บนเครื่องพัฒนา — build หน้าเว็บ แล้วส่งของที่ git ไม่มี (รวม ~890 MB) ไปให้ Pi
cd web && npm run build
scp -r web/dist server/.env server/models server/data kiosk@<ไอพี>:~/Raspberry/...

# บน Pi
cd ~/Raspberry/server
python3 -m venv .venv --system-site-packages     # --system-site-packages ไว้ใช้ picamera2
.venv/bin/pip install -r requirements.txt

sudo cp ../deploy/kiosk-api.service /etc/systemd/system/
sudo systemctl enable --now kiosk-api
cp ../deploy/kiosk-browser.service ~/.config/systemd/user/
systemctl --user enable --now kiosk-browser

bash ../deploy/preflight.sh      # ตรวจความพร้อมก่อนเปิดบริการ
```

| ไฟล์ใน `deploy/` | ทำอะไร |
| --- | --- |
| `kiosk-api.service` | เซิร์ฟเวอร์ · ขึ้นเองตอนบูต · ล้มแล้วกลับมาเอง |
| `kiosk-browser.service` | Chromium เต็มจอ · รอเซิร์ฟเวอร์พร้อมก่อนค่อยเปิด |
| `display-setup.sh` | ปิดการดับจอ ซ่อนเคอร์เซอร์ หมุนจอแนวตั้ง |
| `preflight.sh` | ตรวจเฉพาะสิ่งที่ผิดแล้วเห็นผลตอนมีคนมายืนหน้าตู้ |

> ⚠️ `preflight.sh` จะไม่ยอมให้ผ่านถ้า `KIOSK_SIM` ยังไม่เป็น `0`
> เพราะโหมดจำลองเปิดให้ใครก็ได้สวมรอยเป็นนักศึกษาคนใดก็ได้
